3. THE LIKELY ROOT CAUSE — TOOL TYPE
---------------------------------------------------------------------------

There is no agent *delegation* tool type. The only supported master -> subagent
mechanism is `agent_toolset`:

    tools:
      - tool_spec:
          type: agent_toolset            # <-- this
          name: sales_inventory_data
    tool_resources:
      sales_inventory_data:
        agent_name: DB.SCHEMA.SUBAGENT   # <-- key is `agent_name`, not `agent`

If instead the spec uses `type: agent`, the agent is **created without any
error** and then fails at run time on the first question:

    {"message":"Tool type agent is not valid.","code":"399504"}

That is a nasty trap: CREATE AGENT performs no validation of tool_spec.type at
all. I confirmed that even a nonsense type (`not_a_real_tool_type_xyz`) creates
successfully and only fails when invoked. So a spec can look completely healthy
in DESCRIBE AGENT and still be broken.

Could you send me the output of:

    DESCRIBE AGENT <your_master_agent>;

That will tell us the tool type in one look.

---------------------------------------------------------------------------
4. IMPORTANT MECHANICAL DETAIL
---------------------------------------------------------------------------

`agent_toolset` is **tool inheritance, not delegation.** At run time Snowflake
resolves the referenced agent, reads its tool configuration, and unions those
tools into the calling agent's own tool set. The subagent never runs its own
reasoning loop, and its instructions are not applied.

The practical consequence is the important part: because the tools are
flattened, sql_execution runs *inside the master agent's own turn*. That is
precisely why data_to_chart has a real result set to work with and why charting
succeeds.

So the premise in the original report — "data_to_chart on the Master Agent
consuming data generated by the sql_execution tool running within a Subagent" —
describes an architecture that doesn't exist in that form. There is no nested
agent execution to cross. If you have built genuine nesting some other way (for
example a `generic` tool wrapping DATA_AGENT_RUN in a stored procedure), then
the subagent returns only text, there is no structured result set for
data_to_chart to consume, and you would see exactly the symptom you describe.
That would be worth ruling out.

---------------------------------------------------------------------------
5. TWO OTHER THINGS WORTH CHECKING
---------------------------------------------------------------------------

a) Which client is rendering?
   Your phrase "unrendered chart specification" is exactly what you see when an
   application receives the response.chart event but doesn't render the
   Vega-Lite spec. Snowflake Intelligence renders it natively; a custom app or
   direct REST consumer has to render chart_spec itself. If you are testing
   through anything other than the Snowflake Intelligence UI, this alone would
   explain the report.

b) Privileges — silent failure.
   If the calling role lacks USAGE on the referenced agent, the reference is
   **silently skipped** and every tool it would have contributed disappears. No
   error is raised. The master agent then has no data tool, falls back to prose,
   and never calls data_to_chart. Limits are 5 levels of nesting and 25
   referenced agents.

---------------------------------------------------------------------------
6. ONE CAVEAT, IN THE INTEREST OF ACCURACY
---------------------------------------------------------------------------

While testing I noticed the subagent *also* emitted a chart_spec, even though I
never gave it a data_to_chart tool. Chart generation appears to be available as
an implicit server-side skill in this version, so "the master agent must own
data_to_chart" may be a weaker requirement than the docs imply. It does not
change the conclusion above, but I'd rather flag it than overstate the rule.
